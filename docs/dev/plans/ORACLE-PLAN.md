# Plan: every in-house algorithm answers to someone else's implementation

*Written 2026-10-14, the day #159 landed (671e51bd).*

**Status: P0, P1, P2 and P3 are built (2026-10-14), except P1's fuzz
harness and the new vectors for the shared zlib.vec; see "Done so far" at
the end. P4 onward not started.**

[The dependencies FAQ](https://raku.online/faq/dependencies/) says, in a
table, that Raku++ carries its own big integers, regex engine, Unicode
database, DEFLATE, digests, JSON and CSV instead of linking GMP, PCRE, ICU,
zlib, OpenSSL and a JSON library. The obvious next question, from a user or
from us, is *how do you know yours are right?* This plan is how we answer it
with evidence rather than with "the tests pass".

## What #159 tells us about the tests we have

The bug: `codeLengths` in src/Zlib.cpp took the wrong amount off the Kraft sum
while length-limiting a Huffman tree deeper than 15, so a large, skewed input
produced an over-subscribed code that neither our inflate nor zlib would read.
It shipped although three things were supposed to catch it:

| check | why it did not |
|---|---|
| t/vectors/zlib.vec (99 lines, from real libz) | the largest stream is 420 bytes. A literal/length tree only gets deeper than 15 with a few thousand symbols in a Fibonacci-like distribution, so no vector ever reached the code path |
| t/regression/data-native-zlib.raku round-trips | fixed bodies, none big or skewed enough — the same blind spot |
| t/regression/data-native-zlib-reference.raku (ours against libz, both ways) | nine fixed bodies, the largest `('ab' x 40_000)`, which is repetitive rather than skewed. And it is `#?requires Compress::Zlib`; release.yml installs no modules, so in CI it **skips** (to confirm, P0) |

So the oracle existed and was right; the *inputs* never reached the hard part,
and the one check with an oracle on arbitrary inputs does not run where it
matters. That is the general shape of the risk for every family here:

1. **Fixed small inputs miss size- and distribution-triggered paths** —
   Huffman length limiting, Karatsuba above 96 limbs, Knuth D's rare add-back
   step, a stored block at 65,535 bytes, a match at distance 32,768.
2. **Our encoder and our decoder can share a misunderstanding.** A round trip
   through our own pair proves consistency, not conformance. (#159 happened to
   be caught by our own inflate too; the next one may not be.)
3. **An oracle check that skips is indistinguishable, in a green run, from one
   that passed.**

## Principles

- **Every family has an independent oracle**, and the oracle is never our own
  code: system libz / gzip, `openssl` / `hashlib`, Python's `int`, Unicode's
  own `*Test.txt` files, published suites (NIST CAVP, JSONTestSuite), Rakudo.
- **Inputs are generated to reach the hard paths**, not chosen to look
  typical: sizes either side of every threshold in the code, adversarial
  distributions, and a seeded random stream on top. A failure prints the seed
  and the smallest input it shrank to.
- **Three tiers, by cost:**
  - **A — vectors, every push.** Committed files generated by third-party
    tools (as zlib.vec and digest.vec already are), now including large and
    adversarial cases. Network-free, no tools needed, fast.
  - **B — differential soak, every release and nightly.** `t/oracle/run.raku`
    drives a family with N seconds of generated inputs against a live oracle.
    Needs `python3`, `openssl`, `gzip` *on the test machine* — never for the
    build, so the FAQ's "nothing else runs during the build" stays true.
    When an oracle is missing it fails loudly unless `--allow-missing` is
    given; it never silently skips.
  - **C — fuzzing, decoders only.** The parsers that take untrusted bytes
    (inflate, gunzip, JSON, CSV, UTF-8/16 decode, Str→Int/Rat) under
    libFuzzer + ASan/UBSan. Here the property is "refuse or answer, never
    crash, hang or read out of bounds", and for inflate that is a security
    property.
- **Every new gate shows it can fail.** The acceptance test for the zlib soak
  is that it finds #159 on 671e51bd^ (the repo's existing rule: "before the
  feature every check fails").
- **Assert invariants inside the code, in debug builds.** The encoder can
  check its own Kraft sum is exactly 1 before writing a tree; divmod can check
  `q*b + r == a` and `0 <= r < |b|`. Cheap, and they turn a silent wrong
  answer into a loud one on every input any test ever feeds them.

## Work, in order

  data-native-digest-reference.raku run in any CI lane. If they skip, either
  install the modules in one Linux lane or replace the module dependency with
  a python3 call (simpler: the oracle is then libz itself, not a binding).
- `tools/gen-vectors.raku` is cited as the generator in both .vec headers but
  lives in /Users/ash/raku-modules/{Compress-Zlib,Digest}-Native/tools, not

  masters can be regenerated from this repo.
- Add the debug-build invariants: Kraft sum == 1 before a tree is written;
  `q*b + r == a` in divmod; inflate's decoded length == the gzip ISIZE.

### P1 — zlib, because it just broke and because inflate reads hostile input

- **Generators**: sizes 0..2 MB on a log scale with every boundary (32,767 /
  32,768 / 32,769, 65,535 / 65,536); distributions: uniform random bytes,
  English text, log lines, Fibonacci-weighted symbols (forces depth > 15 on
  the literal tree and > 7 on the code-length tree), long runs (matches of
  258), repeats at distance exactly 32,768, a single byte value.
- **Both directions against python3 zlib**, every level 0–9, all three
  wrappers, every strategy for the libz→ours direction.
- **Tier A**: add twenty of these, chosen to cover each path, to zlib.vec
  (store them compressed; 1 MB plain can be a few KB of stream plus a
  generator description).
- **Tier C**: libFuzzer harness on inflate/gunzip under ASan, seeded with
  zlib.vec; a corpus of the crashes it finds goes into the X lines.
- **Acceptance**: the soak finds #159 on 671e51bd^ within its default budget.

### P2 — Int and Rat (the most-used, and where a wrong answer is silent)

- Differential against python3, operands drawn so their limb counts land on
  1, 2, 17, 18, 19, 95, 96, 97, 200, 2,000 and on mixed sizes; signs mixed;
  values near powers of two and of 10**k (the decimal limb base).
- Knuth D's add-back: craft divisors with top limb at the normalisation edge
  (the standard trick: `b = B**n - 1` patterns and Hacker's Delight's
  cases), since random operands hit it with probability ~2/B.
- Identities that need no oracle, at huge sizes: `(a*b) div b == a`,
  `a == (a div b)*b + a % b`, `gcd(a,b)` divides both, `expmod` vs `**` then
  `%` on small cases, `isqrt(n)**2 <= n < (isqrt(n)+1)**2`, Str → Int → Str.
- Run under `RAKUPP_NO_KERNELS=1` as well, so IntKernel.cpp and BigInt.cpp
  are each checked, not one standing in for the other.

### P3 — Unicode at our own version

- A gate that reads the 18.0.0 test files directly (vendored beside the
  other UCD files in tools/ucd, or fetched once by the gate with a checksum).
  Roast's copies follow Rakudo's Unicode version, so today a table bug in a
  character added since then has no test at all.
- An independent re-derivation: a short script that reads UnicodeData and
  friends *without* sharing code with the generators, asks the engine every
  code point × every exposed property, and diffs. Different code reading the
  same spec is the oracle.

### P4 — digests

Already the best-covered family. Add NIST CAVP SHAVS (ShortMsg, LongMsg,
Monte Carlo) and the HMAC vectors as Tier A, the Monte Carlo set in
particular — 100,000 chained hashes per algorithm catch what single
vectors do not. One slow-lane input past 512 MB to cover the 32-bit length
boundary in SHA-1/SHA-256's bit count (and past 2**61 bytes is infeasible,
so the 128-bit length of SHA-512 gets a code read instead).

### P5 — JSON, CSV, random

JSONTestSuite as Tier A (with `i_` results recorded, not asserted). CSV
against python3 `csv` on random fields. Chi-square on `crypt_random_uniform`.

### P6 — regex/LTM differential against Rakudo

Lowest priority because roast already covers it widely; worth it later for
LTM, which is the subtlest part and has a published spec but no test file.

### P7 — say it on the site

A section on the FAQ page, or its own page, *How do you know they are
correct?*: per family, the oracle, the suite, how many cases, and the command
that reruns it. And one honest line: #159 is the example of what the old
checks missed and why the new ones exist.

## Done when

- every row of the inventory has a Tier A check in CI and a Tier B soak
  that runs before each release (added to RELEASING.md as a gate);
- every decoder has a fuzz harness that has run for a fixed budget with
  no findings open;
- no oracle check can skip silently in a release run;
- the zlib soak, run on 671e51bd^, fails.

## Done so far

### P0 (2026-10-14)

- **The libz cross-check skipped everywhere, as suspected.** release.yml
  installs no modules, and `Compress::Zlib` is not installed on the dev
  machine either: data-native-zlib-reference.raku has been a SKIP in every
  run it ever had outside the session that wrote it. It stays as it is; the
  oracle gate below does its job without a module.
- **tools/gen-vectors.raku is home**, one file for both families
  (`gen-vectors.raku zlib|digest`), with the master copies' headers. The zlib
  half now asks python3's zlib, which is libz, instead of Compress::Zlib
  under Rakudo, so it runs on Raku++. Both regenerate the committed .vec
  files byte for byte on macOS with zlib 1.2.12.
- **The encoder checks its own codes.** Before a dynamic block is written,
  each of its three codes must be complete (one one-bit code allowed for
  distances) and within its length limit, or the call dies naming the code.
  With #159's decrement put back, the first round of the soak reports
  "the code-length code is over-subscribed" instead of a stream nobody reads.
- Not done: the `q*b + r == a` check in divmod. It costs a multiplication
  per division, so it belongs behind a build option; that is P2's to decide.

### P1 (2026-10-14)

- **t/oracle/zlib.raku + zlib-oracle.py**, as specified above, in CI on
  macOS and Linux: five fixed rounds from seed 1000, then 45 s on a fresh
  seed. About 25 rounds a minute here, each 12 bodies, ~50 libz/gzip
  streams, ~48 of ours and ~45 mutants.
- **Acceptance met.** On 671e51bd^ the soak's first round (seed 1000) fails
  on a 3,311-byte body: our own inflate and libz and gzip all refuse our
  stream, "invalid code lengths set". So #159 was reachable through the
  7-bit code-length code with a few KB, not only through the literal tree
  with a megabyte. The same 23 rounds pass on the fix.
- **What it found on the first run, all fixed in src/Zlib.cpp with
  t/regression/zlib-framing-and-code-completeness.raku:**
  - the zlib and gzip trailers were read from the end of the buffer, not
    where the deflate data stops: a zlib stream followed by itself inflated,
    raw deflate ignored bytes after its last block;
  - two concatenated gzip members (`cat a.gz b.gz`, RFC 1952 2.2, which
    gzip -d and every other reader accept) were refused with a CRC error;
  - a block whose distance code has no codes at all, which RFC 1951 3.2.7
    allows for all-literal data and libz reads, was refused;
  - incomplete literal/length and code-length codes, which libz refuses,
    were accepted. Our verdict on every mutant now matches libz's; ~3,000
    mutants since, no divergence.
- Not done yet:
  - **new Tier A vectors.** zlib.vec is shared byte for byte with
    Compress-Zlib-Native, so a vector added here has to land there in the
    same change, and the X lines the findings suggest (multi-member gzip,
    trailing bytes, the crafted blocks) would fail that distribution's C
    today, which has its own copy of the same framing code. Next: port the
    four fixes to the distribution, then add the vectors to both.
  - **the fuzz harness** (Tier C) for inflate under ASan. The soak's mutants
    cover the verdicts but not memory safety under a sanitizer.

### P2 (2026-10-14)

- **t/oracle/int.raku + int-oracle.py**: Int against Python's int, operands
  in limbs around every threshold of src/BigInt.cpp and in the shapes long
  division gets wrong, plus the int64 edges; every op its own plain sub so
  the integer kernels may take it, and CI runs it with and without
  `RAKUPP_NO_KERNELS=1`. ~900 cases a second here.
- **t/oracle/rat.raku + rat-oracle.py**: FatRat against Fraction (as
  `.nude`), rounding ops, `.base-repeating`, and `.Num` of an Int or a
  FatRat against Python's correctly rounded float(), with exact ties.
- Every Raku meaning the oracles encode that Python could read differently
  (negative operands of gcd, lcm, the bitwise ops and shifts; floor `div`
  and `%`; `round` taking a half up) was checked against Rakudo 2026.09
  first. They agree.
- **What they found, all fixed, each with a regression green on Rakudo:**
  - `gcd`/`lcm` on machine Ints took `std::llabs`, which has no answer for
    -2**63: `-2**63 gcd 0`, `-2**63 lcm 1` and every lcm with -2**63 came
    out negative (gcd-lcm-at-int64-min.raku). In the interpreter, so the
    JIT and `--exe` had it too; checked in all three after the fix.
  - Rat and FatRat `.Num` with parts past 2**53 rounded an ulp low on an
    exact tie and just past one: it truncated to 19 decimal digits before
    strtod rounded. Rakudo is right. BigInt::ratioToDouble rounds once in
    binary, ties to even, and bounds huge parts by their leading limbs so a
    14,000-digit FatRat converts in 28 µs (was 820)
    (rat-num-rounds-ties-to-even.raku).
  - `.base-repeating` stopped at 10,000 digits and answered with an empty
    cycle: 1/10007 was wrong. Cap now a million, past which it fails; and an
    integral value has no trailing point, as in Rakudo
    (base-repeating-integral-and-long-cycles.raku).
- **Divergences, and what became of them:**
  - `expmod(a, 0, 1)` is 1, not 0, on both engines (libtommath does not
    reduce a zero exponent). Left; the oracle encodes Rakudo's answer.
  - `expmod` with a modulus of zero or less answered (5 for
    `expmod(3, 5, -7)`, -12 for `expmod(-3, 5, -7)`, 0 for a zero modulus)
    where Rakudo refuses: it now throws X::AdHoc too
    (expmod-modulus-must-be-positive.raku).
  - `(4/1).base-repeating(2)`: Rakudo answers the decimal "4", Raku++ the
    base's own "100". Raku++ keeps "100"; the Rakudo fix is a local branch,
    `fix/base-repeating-integral-radix` in the /Users/ash/rakudo-base-repeating
    worktree, with its roast test on branch `base-repeating-integral-radix`
    in that worktree's t/spec. Not submitted anywhere.
- **The --target=js runtime, checked the same day** (the regressions above
  under JavaScriptCore): `expmod` answered negative residues for a negative
  base and died on a negative exponent; `.base-repeating` was `.base`;
  Rat `.Num` divided two converted doubles; and an integral Num literal
  past 2**63 compiled to an Int. All fixed to agree with the interpreter;
  ratToFloat agrees with Python on 20,000 cases including ties and
  subnormals.
- **Found, then fixed: large gcd was ~130x slower than Rakudo** (14,000-digit
  operands: 0.9 s vs 7 ms), so FatRat.new on big parts could run for
  minutes: Euclid over a quadratic divmod. It is Lehmer's gcd over the
  binary form now, after the factors of two come out (0.8 ms there; 14x
  faster than Rakudo on 475,000-bit odd operands), and int-oracle.py's gcd
  cases reach 2,500 limbs, with Fibonacci neighbours, huge quotients, long
  binary runs and shared powers of two (bigint-gcd-lehmer.raku).
- Not done: the debug-build `q*b + r == a` check in divmod. The oracle now
  covers division from outside at ~900 cases a second; the check would
  only add the inputs other tests happen to feed it.

- **t/oracle/unicode.raku + unicode-oracle.py**, in CI on POSIX, about two
  minutes:
  1. NormalizationTest: every line, all four forms, through Uni and Str
     (403,420 checks); every code point outside Part 1 but the surrogates
     unchanged by all four (4,379,640);
  2. GraphemeBreakTest: every line, as `.comb` and `.chars` (853);
  3. CollationTest_NON_IGNORABLE: every line `unicmp` the next (207,603);
  4. every code point, for the ~90 properties the vendored UCD files define

  fails, or with `--allow-missing` says SKIP. Section 4 needs only python3.
- **What it found, all fixed, with regressions:**
  - `unicmp`/`coll` broke a tie between equal keys on the code points as
    given; UTS #10's identical level is the NFD form, and a Str is NFC. 12
    CollationTest pairs, all on roast's TODO list for Rakudo; Raku++ now
    passes those 13 TODOs too (unicmp-identical-level-is-nfd.raku).
  - Bidi_Class: the generator ignored DerivedBidiClass's `@missing` lines,
    so unassigned code points in the Hebrew, Arabic, Syriac, … blocks were L
    instead of R or AL, and in Currency Symbols L instead of ET (120 ranges).
  - Joining_Type: an unlisted Mn, Me or Cf code point is T, not U
    (ArabicShaping's own note); 376 ranges.
  - Indic_Conjunct_Break answered a Bool; Block answered "" for No_Block;
    Simple_Case_Folding was not there at all (a new SFOLD table).
  - The strings `uniprop` answers for mappings, and `uniparse`'s answer,
    were built from raw code points, so `0x340.uniprop('lc') eq "\x[300]"`
    and `uniparse('GREEK QUESTION MARK') eq ';'` were False; they are NFC now,
    as every other Str (uniprop-against-the-ucd.raku).
  Rakudo 2026.09 shares the first three and the case-folding gaps.
- **Spellings the oracle encodes on purpose, where Rakudo differs:** roast
  pins `Not_Reordered` and `Yes`/`Maybe`/`No`, where MoarVM answers `0` and
  `Y`/`M`/`N`; Hangul_Syllable_Type and Indic_Positional_Category answer the
  short `NA` (MoarVM: `Not_Applicable`). Joining_Group is spelled as roast
  pins it, `SYRIAC WAW`, on both engines; canonical combining classes with
  no name answer their number on both.
- Not done: Vertical_Orientation and Script_Extensions are not exposed and
  their files are not vendored; the deprecated Expands_On_* properties are
  not exposed and the oracle leaves them out. Word, sentence and line break
  and the Bidi algorithm are not implemented, so their test files are not
