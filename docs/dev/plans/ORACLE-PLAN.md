# Plan: every in-house algorithm answers to someone else's implementation

*Written 2026-10-14, the day #159 landed (671e51bd). Nothing here is built
yet.*

[The dependencies FAQ](https://raku.online/faq/dependencies/) says, in a
table, that Raku++ carries its own big integers, regex engine, Unicode
database, DEFLATE, digests, JSON and CSV instead of linking GMP, PCRE, ICU,
zlib, OpenSSL and a JSON library. The obvious next question, from a user or
from us, is *how do you know yours are right?* This plan is how we answer it
with evidence rather than with "the tests pass".

## What #159 tells us about the tests we have

The bug: `codeLengths` in src/Zlib.cpp took the wrong amount off the Kraft sum
while length-limiting a Huffman tree deeper than 15, so a large, skewed input
produced an over-subscribed code that neither our inflate nor zlib would read.
It shipped although three things were supposed to catch it:

| check | why it did not |
|---|---|
| t/vectors/zlib.vec (99 lines, from real libz) | the largest stream is 420 bytes. A literal/length tree only gets deeper than 15 with a few thousand symbols in a Fibonacci-like distribution, so no vector ever reached the code path |
| t/regression/data-native-zlib.raku round-trips | fixed bodies, none big or skewed enough — the same blind spot |
| t/regression/data-native-zlib-reference.raku (ours against libz, both ways) | nine fixed bodies, the largest `('ab' x 40_000)`, which is repetitive rather than skewed. And it is `#?requires Compress::Zlib`; release.yml installs no modules, so in CI it **skips** (to confirm, P0) |

So the oracle existed and was right; the *inputs* never reached the hard part,
and the one check with an oracle on arbitrary inputs does not run where it
matters. That is the general shape of the risk for every family here:

1. **Fixed small inputs miss size- and distribution-triggered paths** —
   Huffman length limiting, Karatsuba above 96 limbs, Knuth D's rare add-back
   step, a stored block at 65,535 bytes, a match at distance 32,768.
2. **Our encoder and our decoder can share a misunderstanding.** A round trip
   through our own pair proves consistency, not conformance. (#159 happened to
   be caught by our own inflate too; the next one may not be.)
3. **An oracle check that skips is indistinguishable, in a green run, from one
   that passed.**

## Principles

- **Every family has an independent oracle**, and the oracle is never our own
  code: system libz / gzip, `openssl` / `hashlib`, Python's `int`, Unicode's
  own `*Test.txt` files, published suites (NIST CAVP, JSONTestSuite), Rakudo.
- **Inputs are generated to reach the hard paths**, not chosen to look
  typical: sizes either side of every threshold in the code, adversarial
  distributions, and a seeded random stream on top. A failure prints the seed
  and the smallest input it shrank to.
- **Three tiers, by cost:**
  - **A — vectors, every push.** Committed files generated by third-party
    tools (as zlib.vec and digest.vec already are), now including large and
    adversarial cases. Network-free, no tools needed, fast.
  - **B — differential soak, every release and nightly.** `t/oracle/run.raku`
    drives a family with N seconds of generated inputs against a live oracle.
    Needs `python3`, `openssl`, `gzip` *on the test machine* — never for the
    build, so the FAQ's "nothing else runs during the build" stays true.
    When an oracle is missing it fails loudly unless `--allow-missing` is
    given; it never silently skips.
  - **C — fuzzing, decoders only.** The parsers that take untrusted bytes
    (inflate, gunzip, JSON, CSV, UTF-8/16 decode, Str→Int/Rat) under
    libFuzzer + ASan/UBSan. Here the property is "refuse or answer, never
    crash, hang or read out of bounds", and for inflate that is a security
    property.
- **Every new gate shows it can fail.** The acceptance test for the zlib soak
  is that it finds #159 on 671e51bd^ (the repo's existing rule: "before the
  feature every check fails").
- **Assert invariants inside the code, in debug builds.** The encoder can
  check its own Kraft sum is exactly 1 before writing a tree; divmod can check
  `q*b + r == a` and `0 <= r < |b|`. Cheap, and they turn a silent wrong
  answer into a loud one on every input any test ever feeds them.

## Work, in order

### P0 — make what exists honest (half a day)

- Confirm whether data-native-zlib-reference.raku and
  data-native-digest-reference.raku run in any CI lane. If they skip, either
  install the modules in one Linux lane or replace the module dependency with
  a python3 call (simpler: the oracle is then libz itself, not a binding).
- `tools/gen-vectors.raku` is cited as the generator in both .vec headers but
  lives in /Users/ash/raku-modules/{Compress-Zlib,Digest}-Native/tools, not
  here, while these copies are the masters. Bring the generator home so the
  masters can be regenerated from this repo.
- Add the debug-build invariants: Kraft sum == 1 before a tree is written;
  `q*b + r == a` in divmod; inflate's decoded length == the gzip ISIZE.

### P1 — zlib, because it just broke and because inflate reads hostile input

- **Generators**: sizes 0..2 MB on a log scale with every boundary (32,767 /
  32,768 / 32,769, 65,535 / 65,536); distributions: uniform random bytes,
  English text, log lines, Fibonacci-weighted symbols (forces depth > 15 on
  the literal tree and > 7 on the code-length tree), long runs (matches of
  258), repeats at distance exactly 32,768, a single byte value.
- **Both directions against python3 zlib**, every level 0–9, all three
  wrappers, every strategy for the libz→ours direction.
- **Tier A**: add twenty of these, chosen to cover each path, to zlib.vec
  (store them compressed; 1 MB plain can be a few KB of stream plus a
  generator description).
- **Tier C**: libFuzzer harness on inflate/gunzip under ASan, seeded with
  zlib.vec; a corpus of the crashes it finds goes into the X lines.
- **Acceptance**: the soak finds #159 on 671e51bd^ within its default budget.

### P2 — Int and Rat (the most-used, and where a wrong answer is silent)

- Differential against python3, operands drawn so their limb counts land on
  1, 2, 17, 18, 19, 95, 96, 97, 200, 2,000 and on mixed sizes; signs mixed;
  values near powers of two and of 10**k (the decimal limb base).
- Knuth D's add-back: craft divisors with top limb at the normalisation edge
  (the standard trick: `b = B**n - 1` patterns and Hacker's Delight's
  cases), since random operands hit it with probability ~2/B.
- Identities that need no oracle, at huge sizes: `(a*b) div b == a`,
  `a == (a div b)*b + a % b`, `gcd(a,b)` divides both, `expmod` vs `**` then
  `%` on small cases, `isqrt(n)**2 <= n < (isqrt(n)+1)**2`, Str → Int → Str.
- Run under `RAKUPP_NO_KERNELS=1` as well, so IntKernel.cpp and BigInt.cpp
  are each checked, not one standing in for the other.

### P3 — Unicode at our own version

- A gate that reads the 18.0.0 test files directly (vendored beside the
  other UCD files in tools/ucd, or fetched once by the gate with a checksum).
  Roast's copies follow Rakudo's Unicode version, so today a table bug in a
  character added since then has no test at all.
- An independent re-derivation: a short script that reads UnicodeData and
  friends *without* sharing code with the generators, asks the engine every
  code point × every exposed property, and diffs. Different code reading the
  same spec is the oracle.

### P4 — digests

Already the best-covered family. Add NIST CAVP SHAVS (ShortMsg, LongMsg,
Monte Carlo) and the HMAC vectors as Tier A, the Monte Carlo set in
particular — 100,000 chained hashes per algorithm catch what single
vectors do not. One slow-lane input past 512 MB to cover the 32-bit length
boundary in SHA-1/SHA-256's bit count (and past 2**61 bytes is infeasible,
so the 128-bit length of SHA-512 gets a code read instead).

### P5 — JSON, CSV, random

JSONTestSuite as Tier A (with `i_` results recorded, not asserted). CSV
against python3 `csv` on random fields. Chi-square on `crypt_random_uniform`.

### P6 — regex/LTM differential against Rakudo

Lowest priority because roast already covers it widely; worth it later for
LTM, which is the subtlest part and has a published spec but no test file.

### P7 — say it on the site

A section on the FAQ page, or its own page, *How do you know they are
correct?*: per family, the oracle, the suite, how many cases, and the command
that reruns it. And one honest line: #159 is the example of what the old
checks missed and why the new ones exist.

## Done when

- every row of the inventory has a Tier A check in CI and a Tier B soak
  that runs before each release (added to RELEASING.md as a gate);
- every decoder has a fuzz harness that has run for a fixed budget with
  no findings open;
- no oracle check can skip silently in a release run;
- the zlib soak, run on 671e51bd^, fails.
