# 100% of Roast

**Reached in v5.0.0 (2026-09-29).** On Roast `1f521d798` and the 1,424 files of
its `spectest.data`, Raku++ passes 218,421 of 218,422 tests with Roast's skip
and todo left out, 220,054 of 220,055 with them counted as passes, and 1,423
of the 1,424 files. The one failing test is test 3 of `S16-io/eof.t`: Roast
marks it todo on macOS by release name, and the machine of record runs macOS
27, which the list does not name. The measurement and the per-synopsis table
are in [ROAST.md](../../status/ROAST.md).

This page began on 2026-08-02 as an argument that 100% does not exist. That
analysis is kept below as written; this section says how it turned out.

## Why "100% doesn't exist" did not hold

The ~96.9% was Rakudo on the **raw** files, before the harness applied Roast's
fudge directives. The bar changed in two ways:

- The harness now applies `#?rakudo skip` and `#?rakudo todo` as Rakudo's own
  spectest does ([COUNTING.md](../../status/COUNTING.md)), and the headline
  leaves the skipped and todo tests out. The tests the August text counted as
  unreachable — ones Rakudo itself cannot pass — are exactly the ones Roast
  marks.
- The default file list is `spectest.data`, the files Rakudo's spectest runs,
  not every `.t` in the checkout.

On that bar Rakudo 2026.08 passes 1,414 of the 1,424 files; Raku++ passes all
ten it does not, six of them S05 tests newer than that Rakudo release. The raw
figure was not measured again and still means what it meant; it is not the bar
a release is measured on.

The path: ~74% of raw assertions in August, 200,843 of 219,610 (91.45%, raw) at
v4.0.1, 100.00% fudged at v5.0.0.

## How the five walls turned out

1. **Grammars and LTM.** True longest-token matching became the default on
   2026-08-08 (v3). S05 passes 85 of 85 files.
2. **MOP depth.** `.^add_method`, `augment`, one role per parameterization
   (v5), and a module-supplied metaclass whose `new_type`, `add_attribute`,
   `add_method` and `compose` are each dispatched. Rakudo also calls
   `add_method` after `compose` for the methods it generates; Raku++ does not.
3. **Compile-time execution.** `BEGIN`, constants and operators declared
   mid-file pass their Roast tests. One gap is known outside
   Roast: a `use` inside a closure runs when the closure first runs, not at
   compile time, so a type it imports is unknown where the closure's own
   arguments name it. JSON::Tiny's `t/01-parse.t` fails its last test on this.
4. **Real concurrency.** Threads run in parallel by default since v3
   (`RAKUPP_GIL=1` restores the lock). S17 passes 95 of 95 files;
   `S17-channel/stress.t` runs 7–12 s against the 10-second ceiling and can
   time out on a loaded machine.
5. **Resumable exceptions.** `.resume` continues after the throw when the
   `CATCH` sits in the block that threw. Across a routine call it does not: the
   call returns an undefined value and the rest of the routine is skipped,
   where Rakudo continues inside the routine. No Roast file tests that case.

## What 100% does not cover

Roast is the specification. It does not measure the ecosystem (1,019 of 2,547
distributions pass their own tests; Rakudo passes 1,791 of 2,529), the module
battery (48 of 59 against Rakudo), or speed (v5.0.0 is 5–25% slower than v4.0.1
on the perf-guard kernels). Those are the v5.x and v6 work
([VERSIONS.md](VERSIONS.md)).

## The August analysis (2026-08-02)

### First: 100% doesn't exist

We measured Rakudo itself on the raw files: **~96.9%**. Roast is aspirational in places — it contains tests marked `#?rakudo todo` that the reference implementation cannot pass, tests for `::=` binding that's NYI in Rakudo, timing-sensitive S17 files that flicker even on MoarVM. So the true ceiling is roughly **97%**, and the honest phrasing of the goal is *"pass everything Rakudo-moar passes."* Against the full ~206k denominator we're at ~74%, so the real gap to the ceiling is ~23 points ≈ ~47k assertions.

### What's just labor (most of the gap, no wall)

Judging by how the last 30 points fell, I'd say **half to two-thirds of the remaining gap is grind, not walls**:

- **One-construct parse aborts on big files** — `Rat.new` gates 869 declared tests, postfix `i` gates 557, one `[\(…)]` gates 580. These are days, not months.
- **The `.new` batch** — `Version`, `Duration`, `SetHash`, `buf8`, shaped arrays. Plumbing.
- **252 partials losing 1–2 tests each** — pure long tail.
- **Exception fidelity** — a lot of roast asserts the *exact* `X::` type and `.message` text of errors. That's not a language feature; it's matching Rakudo's error strings one at a time. Unbounded but trivial per item.

### The real walls (where the architecture gets tested)

Ranked by how much I'd respect them:

1. **The full grammar engine.** S05 is the largest synopsis. Our `Regex.cpp` is a capable custom engine, but real Raku regexes are *grammars*: protoregexes with **Longest Token Matching**, action classes, `<~~>` recursion, dynamic subrule dispatch, `:ratchet` semantics interacting with backtracking control. LTM in particular isn't a feature you bolt on — it's a compilation strategy (build NFAs over all candidate tokens, run them in parallel). This is the single biggest block of unreachable tests and needs genuine design work, not patches.

2. **MOP depth.** We have enough metamodel to introspect, but roast tests parametric roles, `augment`, `.^add_method` at runtime, custom HOWs, role conflict resolution corner cases. Raku's object system is defined *by* its MOP; ours is defined by C++ classes with a MOP-shaped surface. Every layer deeper costs a real refactor.

3. **Compile-time execution.** In Raku, `BEGIN` runs *during parsing*, `constant` folds at parse time, `use` imports affect the grammar mid-file, custom operators become parseable the moment they're declared. We fake several of these convincingly, but the honest statement is: Raku is defined as a language whose compiler runs the language, and a tree-walker with a separate parse phase can only approximate that. Some tests can tell the difference.

4. **Real concurrency.** The GIL runtime passes a surprising amount of S17, but stress files (`many-processes`, fd-limit tests, scheduler timing) test *actual parallelism* and OS-level process management. Passing them means true multithreading — the deepest surgery on the interpreter core. Even then, some of these are flaky on Rakudo; this class has a permanent noise floor (our two files that flip 400↔402 with load are the small preview).

5. **Resumable exceptions.** `.resume` means an exception handler can continue execution *at the throw point* — a continuation, essentially. It's currently our only construct that literally wedges the harness (`try.t`). A tree-walker can implement it (re-enter the eval stack), but it cuts across every `throw` path.

### The shape of the curve

The first 80% came from big buckets — fudge support was +19 files in one change, Unicode data was +4k assertions. The remaining buckets get monotonically smaller: after the `Rat.new`-class wins land, we're into territory where a day of work buys 5–20 assertions. Nothing *stops* us before ~90–92% with the current architecture — that's reachable by grind plus the parse-blocker list in ROAST-GAPS item 8. The band from ~92% to the ~97% ceiling is where the four walls above live, and each one is a project, not a task.

So: no mystery, no single dragon. One fake wall (100% isn't real), a wide moat of labor we've been crossing at a steady rate, and four real walls — grammars/LTM being the tallest — that would each deserve a design document before an implementation.
