# The sitting that made `ValueList` its own container

*2026-09-02. Two items, in the order they turned out to want. Everything here
landed as commits `0fc8dae` and `639aee5`; the detailed records are
[VALUE32-PLAN.md](../plans/VALUE32-PLAN.md) (what the changes are and what
they measured), [IR-EXPERIMENT.md](IR-EXPERIMENT.md) (the re-measurement) and
[RELEASE-DELTA-v3.24.0.md](../findings/RELEASE-DELTA-v3.24.0.md) (this tree
against the shipped release). This file is the narrative, and it is written
mostly around the four things that went wrong, because those are the parts
that do not survive in a commit message.*

## The question, and which half to answer first

Two candidates were on the table. From
[PERL5-TECHNIQUES.md](../findings/engines/PERL5-TECHNIQUES.md), item 3: take
perl's flat threaded execution loop, `while ((PL_op = op = op->op_ppaddr(aTHX)));`,
and stop re-dispatching a tree. From [VALUE32-PLAN.md](../plans/VALUE32-PLAN.md),
the two cheap items its probe had turned up on the way to a smaller `Value`.

The order was not a preference. Two things in the repo already decided it.
The plan's own falsifier says that if the relocating `ValueList` collects most
of the array-path win on its own, then the whole size campaign is competing
with a change an order of magnitude smaller and has to be re-priced — so that
measurement has to exist before design A is worth starting. And the flat loop
had already been measured and rejected here, on 2026-08-08, in
[IR-EXPERIMENT.md](IR-EXPERIMENT.md). Starting a large campaign against a
recorded falsification without re-taking the measurement would have been the
wrong move; re-taking it is cheap.

So: the `Value` items first, then the flat loop as a measurement rather than
a project. Both were done.

## What landed

Four changes, all in one new file, [src/ValueVec.h](../../../src/ValueVec.h):

1. **`ValueList` is `RVec<Value>`, not `std::vector<Value>`.** It grows in ONE
   pass — construct the new element, destroy the old, per element, in a single
   walk — where `std::vector` fills a second buffer and then walks the old one
   again to destroy it.
2. **Where the standard library tolerates a bitwise move, that pass is a
   `memcpy`.** `Value` is trivially relocatable; the exception is the
   `std::string` inside `CowStr`, and `bitwiseRelocOk()` asks the library at
   run time rather than trusting a macro.
3. **Small blocks come off a thread-local free list**, kept per exact capacity
   for capacities 1 through 4. The tree's most frequent `ValueList` by far is
   the one- or two-element argument list built on every interpreted call, and
   its heap block was the whole of its cost.
4. **`CowStr::kPromote` 64 → 23**, libc++'s small-string boundary.

Against the session's starting binary, minimum of five runs, instructions and
cycles: arrayops 1.303/1.201, listbuild 1.259/1.223, sortnums 1.188/1.201,
multimeth 1.139/1.136, a two-argument call loop 1.130/1.088, textsplit
1.116/1.111, fib 1.086/1.043, hashfill 1.054/1.051. Nothing below parity.

## Four things that went wrong

### 1. Wall clock said `fib` had regressed 2.4%. It had not.

The container's first build read 2.4% slower on `fib` and 2.1% on `strpass` by
wall clock, which is the shape of a real per-call regression and was treated
as one. Two rounds of design changes were made to chase it — the growth policy
was backed out of rounding the first block up, and the grow path was
restructured — and the reading did not move.

Instruction counting ended it in one command: `fib` retires **+0.14%**
instructions on the new container, and a standalone probe of the exact
call-path shape (build a one-element list, hand it to a function by value,
destroy it) puts `RVec` **ahead** of `std::vector` by 1.088×. The remaining 1%
of cycles is code layout in a translation unit whose object code had shrunk by
311 KB. Nothing was wrong.

The cost of the mistake was two build-and-measure cycles and one design
decision made for a reason that turned out to be false — the growth policy is
still the right one, but the paragraph justifying it had to be rewritten
around the real reason, which arrived two hours later and is about memory.

### 2. The relocation probe was wrong, and only the speed suffered

`bitwiseRelocOk()`'s first version asked whether a short string's `data()`
pointer lay inside the string object. It does — on every implementation, that
is what the small-buffer optimisation *is*. So the probe answered "not
relocatable" everywhere, libc++ included, the `memcpy` path never ran, and
every number measured that day came from the fallback loop.

It was caught by asking the binary a question nobody had asked: a five-line
program printing which path was live. The right question is whether the object
holds a *stored pointer* to those characters — libstdc++ aims `_M_p` at its own
`_M_local_buf`, libc++ and MSVC compute the address from `this` — and the
probe now relocates a string and checks where the copy's characters come from.

Two lessons, and the second is the general one:

- **Most of the win was never the `memcpy`.** Turning it on afterwards added
  `listbuild` +6.1% cycles, `arrayops` +4.2%, `sortnums` +1.1%, and nothing
  elsewhere. The one-pass walk is worth more than the bitwise move.
- **A correctness-preserving fallback can hide a dead fast path indefinitely.**
  Nothing failed. No test could have failed. The only symptom was a number
  that was smaller than it should have been, in a project where nobody knew
  what it should have been.
  [tools/reloc-probe.cpp](../../../tools/reloc-probe.cpp) exists so the
  question has an answer that does not require reading the header.

### 3. The free list's first block size cost 56% more memory

The obvious free list rounds every small request up to one four-element block:
one size class, one list, simplest possible code, and slightly faster than the
alternative. It measured well on every call-shaped kernel.

It also made a program holding a million one-element arrays go from 292–296 MB
to 560–663 MB, and pay 22% of its cycles in the extra memory traffic. A
`ValueList` is not only an argument list — it is the payload of every Array
`Value`, and the two uses want opposite things from a block-sizing policy.
Per-capacity lists keep the allocation win and leave the footprint alone.

This is the same lesson batch 4 of the representation campaign wrote down in
different words: a census of what typical programs do bounds neither what the
language allows nor what a *different* user of the same structure needs.

### 4. Two agreeing single runs agreed on a wrong number

The `kPromote` change was published, in this file's ancestor, as an 8.9% win
on grammar JSON parsing. It is 0.1%.

The measurement was one run per binary. It was taken twice, on different
corpora, and both times said 8–9%, which felt like confirmation. It was not:
the grammar parse's instruction count spreads ±1.9% run to run **on an
unchanged binary**, and the two readings had agreed on a value about 12% above
the kernel's own floor. `fib`, measured the same way, repeats to ±0.02%.

The mechanism is predictable in hindsight and worth stating because it is
predictive: the variance is the parallel runtime's workers doing variable
work, so it lands on kernels that allocate and thread, and not on tight
arithmetic loops. The rule is now in
[PERF-CAMPAIGN.md](PERF-CAMPAIGN.md): measure a kernel's spread on one binary
before trusting any ratio from it, and quote the minimum of at least five
runs. Item G's table in the plan is the second one that section has had, and
the corrected version is narrower and honest — one real workload at 3%, a
synthetic best case at 20%, a measured counter-case at −5.6%, flat elsewhere.

## The flat loop, re-measured

Perl's item 3, asked directly, re-priced against today's tree rather than
quoted from August. The verdict is unchanged in direction and changed in
reason.

**Still no.** The opcode `switch` alone is 0.32 ns. A node visit costs 46–85 ns
(`fib` 46, `asg` 61, `call` 65, `loopsum` 72, `method` 85, from a
`-DRAKUPP_NODE_COUNT` build). Flat dispatch is 0.4–0.7% of a node visit. The
interpreter is not slow because it walks a tree.

**But one leg of the old verdict broke.** The escape-analysis crossing tax —
what it costs to park an interpreter intermediate in addressable storage
rather than a non-escaping local — was +11.2 ns per un-lowered node in August
and measures **−0.02 ns** now. It was a property of a 376-byte `Value` with
five `std::string`s and eleven `shared_ptr`s; at 128 bytes it has vanished,
and with it the ~42% break-even that made a partial lowering impossible. An
IR could now be introduced incrementally. It still has no motive, and the
thing that would give it one is unchanged: unboxed typed registers.

What the same file had recommended *instead* was the per-call `Env` and the
per-call argument `ValueList`. The first had been softened by the frame pool.
The second had not been touched, and it is what change 3 above is: 32.35 ns to
9.48 ns on the shape, `fib` +8.8% instructions, a two-argument call loop
+13.0%. The flat-loop question paid for itself by naming the work, which is
not the same as being worth doing.

## Against what a user downloads

Separately, and afterwards: the tree measured against
`rakupp-macos-universal.tar.gz` from the v3.24.0 GitHub release. Four binaries,
so build configuration and code do not get confused — the release, the same tag
built locally, HEAD, and HEAD plus this work.

The CI universal build is fair: within 1% of a local build of the same commit
on 25 of 26 kernels. The exception is `bigint`, where the release retires 5.2%
*more* instructions than a local build of the same source.

Against the release this tree retires 2–29% fewer instructions on 20 of 26
kernels. Two read below it — `asg` at 0.986 and `loopsum` at 0.983 — and
splitting the delta says why: the 36 commits between v3.24.0 and HEAD cost
1–2% broadly and 9–12% on grammar parsing. Bisecting the assignment case found
one line, `tctx_.curStmtExpr = e;` in the `ExprStmt` arm of
`Interpreter::exec`, costing ~34 instructions per statement executed through a
thread-local resolution. Deleting it is not the fix; it is load-bearing for
cooperative `next`/`last`/`redo`. The grammar-parse loss is larger and still
un-bisected.

That the concurrency chapter had already written this exact trap down —
"a `thread_local` costs a TLV lookup per statement on macOS — measured +6% on
`loopsum`" — and it was walked into again, on a field that cannot simply be
deleted, is the fifth thing that went wrong this sitting. It just was not ours.

## Gates

`t/run.raku` 631/631 with a new case covering the corners a hand-written
container gets wrong. `t/stress/run.raku` 26/26 after each change. Four full
Roast runs, per-file diff jitter only, every apparent loss re-run serially
under both binaries and identical. ThreadSanitizer showing the same five
pre-existing `-parallel` failures under the new binary and under a control
built from the same tree with the typedef reverted, re-run after the free list
landed and again after the `memcpy` path went live.

## Open

- The `tctx_.curStmtExpr` store: set it only for statements whose expression
  can hold a bare loop control, or hoist the thread-local resolution to the
  top of `exec`.
- The grammar parse's 9–12%, un-bisected, larger than the statement store.
- Design A of [VALUE32-PLAN.md](../plans/VALUE32-PLAN.md) — 56 bytes — now
  re-priced by this sitting: the array-path kernels moved 3–12% for a change
  that touches one typedef, so a 56-byte `Value` should be expected in that
  band rather than in the probe's 5×, and A's ~190 ownership sites weighed
  against it.
