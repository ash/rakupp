Why
why a second implementation

A language is more than one compiler.

the spec

Two engines ask questions

Every place two independent implementations disagree is a question about what Raku actually means. One engine can't ask it of itself.

the shape

No VM to start

A single native binary: about 4 ms to start interpreting, with nothing to install beside it. Fast enough to call from a shell loop.

the reach

Places Rakudo doesn't go

A standalone native executable, a page in the browser through WebAssembly, an Arduino board, a library embedded in Python, Go or Rust.

the code

C++17, no dependencies

A hand-written lexer, parser, regex engine, bignum and Unicode tables. CMake and a C++17 compiler are all it needs.

  • This is not "Rakudo is bad". Rakudo is the reference, and the Thanks slide says so.
  • Use the spec argument as the main reason; the others are what it gives in practice.
Restraint
the one deliberate limit

The program can't rewrite the parser.

No slangs and no macros. A program that can't change its own grammar at run time has a parse tree that is known ahead of time, and a tree known ahead of time can become C++. That one restraint is what makes --exe, --aot and --target=js possible.

still there

What the parser does handle

User-defined operators in all six categories with precedence traits, meta-operators over them, RakuAST as a view (.AST, .DEPARSE, .EVAL), and use L10N::DE as a rewrite of the token stream.

not there yet

The honest list

Macros and slangs; C structs passed or returned by value; callbacks a C library fires from its own thread; some IO and POD corners.

  • Say the "not there yet" list yourself, before someone asks.
  • Roast still passes 100%: what's missing is what Roast doesn't require, or marks todo.

Core
the pieces that took the most work

Small values, exact numbers, real Unicode.

value

32 bytes, refcounted

Every Raku value fits in 32 bytes. There is reference counting and no tracing GC, so memory comes back when the last reference goes.

numbers

An exact tower

Our own BigInt (base 10⁹ with a machine-word fast path) and Rat, so 0.1 + 0.2 == 0.3 is True. Untyped arrays of Ints are kept as machine words.

unicode

Graphemes first

UAX #29 graphemes, NFC/NFD/NFKC/NFKD, names and properties from UCD 18.0, and UCA collation: all 8,271 conformance tests pass.

regex

Our own matcher

A continuation-passing backtracking matcher with LTM, :my variables set mid-match, and grammars on top. YAMLish is what pushed it.

dispatch

multi, proto, where

Type, literal and where constraints, callsame and friends, the same rules for the interpreter and the compiler.

threads

Real OS threads

start, await, Supply, react, Channel, hyper, and --detect-races to show where threads collide.

Everything skipped today is in Raku++ Internals, the book: about 45 chapters in docs/book/.

  • Pick two cards to talk about; don't read all six. Suggestion: numbers (the Mandelbrot story) and Unicode.
  • Mandelbrot: a Rat whose denominator overflows 64 bits must fall back to Num, which only showed up as wrong pixels.

Test
how it is tested

Gates, and an oracle.

gate 1 · ~6 min

All of Roast

1,425 files through a harness written in Raku and run by Raku++ itself. The rule: no fully passing file may regress.

gate 2 · ~20 min

t/run.raku

2,353 checks: regressions, --exe, --aot, JS, JIT, slim binaries, races, the sandbox, Arduino, leaks, Windows paths.

gate 3

perf-guard

A fixed set of kernels timed before and after. Speed counts as a regression too.

The compiler isn't graded against Roast but against the interpreter: compile a program, run both, and compare the output byte for byte. As of v5.8.0, --exe agrees on all 1,573 example and regression programs.

  • Self-hosting point: the tool that measures the compiler runs on the compiler.
  • The "interpreter as oracle" idea is worth a pause; people like it.

Meaning
reading the number honestly

What 100% does and doesn't say.

it says

The language, in the small

Every feature Roast isolates behaves as written down. On the older Roast 1f521d798, measured the same way on the same machine, Raku++ v5.1.0 passed 1,423 files and Rakudo 2026.08 passed 1,414.

it doesn't say

Real programs work

Roast isolates features, while real code combines a dozen modules at once. Numeric context on an array, nested hash access and pair keys all passed Roast and still printed wrong output in real code.

So Roast is the floor, not the finish. Next comes everything it never tests.

  • Be careful with the Rakudo comparison: it was on the older Roast commit, and Rakudo isn't being judged here. Roast todos are written for Rakudo.

Run modes
one source, many targets

More than an interpreter.

--bundle / --aotStandalone binary that carries the source, or the already-parsed AST.
--exe -o progTranspile to C++ and compile native. Anything unsupported falls back to --bundle automatically.

Speed
times faster than Rakudo 2026.09 · v5.5.0 on an Apple M4 · log scale

Interpreted, and compiled.

interpreted--exe
Startup: 4.4 ms interpreting and 3.1 ms for a native binary, against Rakudo's 62.5 ms. --exe is ahead on all eighteen kernels, though only just on objects and multiwhere, where MoarVM's spesh does its job (and multiwhere's binary bundles the interpreter).
  • These are small kernels, including startup. Don't over-claim; v6 is the release about speed.
  • The M4 is standing in for the usual M3, so compare by ratio, not milliseconds.

Arduino
rakupp --target=arduino

Raku as firmware.

use Arduino; pinMode(LED_BUILTIN, OUTPUT); say "blink"; loop { digitalWrite(LED_BUILTIN, HIGH); delay(500); digitalWrite(LED_BUILTIN, LOW); delay(500); }
  • ▹The program becomes one C++ sketch that names no runtime.
  • ▹The same file runs without a board too, on a simulated one, interpreted or compiled; the gate checks both byte for byte.
  • ▹Tried on an Uno R4 WiFi, LED matrix and network included, and built for Uno, Due and R4 cores.
  • ▹Raku while building: every constant is computed on your computer in full Raku (sin, .map, a file, use JSON::Native); the board gets only the result, stored in flash.

Chicken & egg
the installer can't install its own dependencies

zef needs a JSON parser before modules exist.

# what zef does, in effect: my \JSON = ::("Rakudo::Internals::JSON"); my %meta = JSON.from-json($file.slurp); # reached dynamically: it compiles anywhere, # and fails only at run time
  • ▹Every META6.json is JSON, so the installer must parse JSON before it can install a JSON parser.
  • ▹On a bare Rakudo, the only JSON parser you can count on is the one the compiler carries for its own use.
  • ▹So an internal class became load-bearing public surface in all but name.
  • Tell it as a story: we ran zef, it reached for a class that exists in no specification.
  • The blame isn't on zef: there's no dependency-free standard library for JSON, platform checks or directory walks.

nqp & VM
two more places where the implementation leaks through

nqp:: ops, and an unknown VM.

use nqp

JSON::Fast's hot paths

JSON::Fast sits under about 170 distributions, and it reaches for nqp::iseq_i, nqp::substr, nqp::push_s. NQP is Rakudo's bootstrap language, documented as internal and unspecified. So Raku++ implements the subset the ecosystem actually uses, with NQP's native-integer semantics.

$*VM.name

"Unknown VM; don't know how to build"

On Raku++, $*VM.name is cpp, and build scripts that only know moar or jvm stop. RAKUPP_VM_NAME gets past them, and rakupp install LibraryMake retries the test as moar by itself, and says so.

Neither one is a bug in those modules. Both come from one implementation having been the only one for a long time.

  • Optional demo: use nqp; say nqp::add_i(2, 3) on rakupp.
Two names
rakupp's policy for Rakudo's internals

Answer the alias, own the name.

first-party

Rakupp::Internals::JSON

Our own C++ codec under our own name, and what rakupp's own tools call. A typo'd Rakupp:: name is still an error: the namespace mustn't swallow mistakes.

compatibility

Rakudo::Internals::JSON

The same codec under Rakudo's name, so zef, OpenSSL and Pakku run unchanged. On plain data the text is Rakudo's; on a Set or an object it's JSON::Fast's.

Removing the alias isn't realistic while zef itself calls it. The plan of record: the Rakudo spelling will eventually say out loud that a program leans on another implementation's internals. That's a note, not a refusal.

  • Only the class name is Rakudo's; the code is original.
  • A bug caught here: JSON::Native's value-by-value suite showed the codec accepted trailing content. Fixed in 9072beb.
::Native
our ::Native modules, on the JSON example

JSON::Native: one name, the engine's codec.

use JSON::Native; say to-json({ ok => True }, :!pretty); # {"ok":true} say json-backend(); # engine
  • ▹A normal distribution (META6, installed by zef) that the engine also answers itself: no file read, nothing installed.
  • ▹The contract is JSON::Fast's, down to the byte. What the C++ codec doesn't cover goes to a pure-Raku port of JSON::Fast built into the binary.
  • ▹The engine steps aside when an installed copy is newer, when -I or use lib points at it, or when you ask for a :ver. So the module's own suite always tests its own code.
  • ▹Same idea: CSV::Native, Digest::Native, Compress::Zlib::Native.
  • History: it started as Rakupp::JSON and was renamed four days later. Name a module for what it does, not for the engine it's fastest on.
  • The earlier rule was "the compiler must not special-case a module name". The steps-aside list is what keeps that rule's purpose.
Data::Native
the missing standard library, as one use

One use for what the engine already does.

use Data::Native; say to-json({ ok => True }); say from-csv("a,b\n1,2\n", :headers); say sha256-hex('abc'); say uncompress(compress('big'.encode)); say crypt_random_buf(32);
  • ▹Five tags (json, csv, digest, zlib, random bytes), thirty-two names. use Data::Native <json csv> takes just those.
  • ▹A program using it compiles to a standalone binary, with nothing to load.
  • ▹The design: on another engine, the same line loads a distribution of the same name built from the usual ecosystem modules. That's portable, not Raku++-only.
  • ▹Honestly: that companion distribution isn't published yet.
  • Link back to the chicken-and-egg slide: this is the dependency-free standard library whose absence made zef reach into Rakudo's internals.
