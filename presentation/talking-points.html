Part 1 · what and why

What it is: the opening claim

Raku++ · Timeline · Why
From scratch, not a fork
A complete implementation of Raku in C++17 with no third-party dependencies: a hand-written lexer, parser, tree-walking evaluator, bignum, Unicode tables and regex engine. It shares no code with Rakudo, and it studies Rakudo and MoarVM at the level of design, porting nothing.
Four and a half months
First commit 2 July 2026; 4,068 commits and 53 tagged releases since, each one gated on Roast and the local suite. v5.8.0 (12 November) is the release where every Roast file passes and --exe agrees with the interpreter on all 1,573 example and regression programs. The method never changed: measure, find what fails, fix it in general, and never special-case a test or a module.
Why a second engine

The spec. Every place two independent implementations disagree is a question about what Raku means, and one engine can't ask it of itself. This is the main reason; the rest are what it gives in practice.

The shape. One native binary with no VM to spin up: about 4 ms to start, fast enough to call from a shell loop.

The reach. A standalone executable, a browser page through WebAssembly, an Arduino board, a library inside Python, Go or Rust, an app on a phone.

Measured against Roast
The official specification suite is the target and the scoreboard. The motto: any compiler that can run Roast can be officially called a Raku compiler. The harness is written in Raku and run by Raku++.
Two revisions, gated
6.d by default, 6.e under use v6.e.PREVIEW: 50 of 51 tracked 6.e changes match Rakudo. The revision belongs to the code: a 6.e module keeps its semantics inside a 6.d program without changing that program's own, where Rakudo's use of a 6.e module loads CORE.e for the whole process.

The one deliberate limit

Restraint

The program can't rewrite the parser. Say it as a design choice, because it is one.

No slangs, no macros
A program that can't change its own grammar at run time has a parse tree known ahead of time, and a tree known ahead of time can become C++. That restraint is what makes --exe, --aot, --target=js and --target=arduino possible. Pluggable syntax would need a grammar object to mix a role into; the plan is written, and emulating one was rejected.
What the parser still does
User-defined operators in all six categories with precedence traits, meta-operators over them, the operator table changing mid-parse in one pass; RakuAST as a view (.AST, .DEPARSE, .EVAL); and use L10N::DE as a rewrite of the token stream, because a keyword table is not a grammar change.
Roast still passes
What's missing is what Roast doesn't require or marks todo. The full "not there yet" list is in Have these ready; say it yourself, before someone asks.

Part 2 · architecture

One front end, many back ends

Architecture
The pipeline
Source (UTF-8, graphemes from the start) → a hand-written, context-aware lexer → a recursive-descent parser that knows user operators → an AST, fixed once parsed → node specialisation, which rewrites nodes for the types they meet. Then one of six back ends.
The back ends
The tree-walking interpreter (the whole language); --aot, the AST serialised into a binary; --exe, C++ code generation compiled native; --target=js; --target=arduino; and Raku.js, which is the interpreter compiled by Emscripten, not a separate implementation.
The book
Everything the talk skips is in Raku++ Internals, about 45 chapters in docs/book/.

The pieces that took the most work

Core

Pick two on the slide; don't read all six. Suggested: numbers (the Mandelbrot story) and Unicode.

32-byte values, refcounted
Every Raku value fits in 32 bytes. There is reference counting and no tracing GC, so memory comes back when the last reference goes. sizeof(Value) started at 392 bytes, and shrinking it never dropped the refcounts.
An exact tower

Our own BigInt (base 10⁹ with a machine-word fast path) and Rat on BigInts, Num, Complex and allomorphs. Untyped arrays of Ints are kept as machine words.

say 0.1 + 0.2 == 0.3;     # True, exactly
say 2 ** 1000;            # all 302 digits
say (1/3 + 1/6).nude;     # (1 2)

The Mandelbrot story: a Rat whose denominator overflows 64 bits has to fall back to Num, and that only showed up as wrong pixels.

Graphemes first
UAX #29 graphemes, NFC/NFD/NFKC/NFKD, names and properties from UCD 18.0, UCA collation. Detail in Unicode.
Our own matcher
A continuation-passing backtracking matcher with real LTM, :my variables set mid-match, and grammars on top. YAMLish is the module that pushed it hardest.
Dispatch, threads
multi/proto with type, literal and where constraints and callsame and friends, by the same rules in the interpreter and the compiler. Real OS threads: start, await, Supply, react, Channel, hyper, and --detect-races to show where threads collide.

Part 3 · how we build and test

One CMake build, every platform

Build
The platforms
macOS as one universal binary (Apple Silicon and Intel). Linux x86_64 and ARM64 with static libstdc++, glibc 2.18 and up, plus a musl leg in CI. Windows x64 with a static CRT and no redistributable, from MSVC or MinGW. RISC-V cross-compiled and tested under emulation, and built from source on a 64-core Milk-V Pioneer; OpenBSD. And WebAssembly: the same src/ through Emscripten.
No third-party libraries
CMake and a C++17 compiler are all a build needs. OpenSSL, libffi and the like are loaded through NativeCall at run time, only when a module asks for them, and never linked. CI builds and smoke-tests every leg on every push.
Ways in
curl -fsSL https://raku.online/install.sh | sh
brew install ash/rakupp/rakupp             # macOS

Plus a no-admin PowerShell one-liner and an Inno Setup wizard on Windows, prebuilt archives on GitHub Releases, a GNU Guix channel and a Nix flake.

Gates, and an oracle

Test
Gate 1 · all of Roast
1,425 files through a harness written in Raku and run by Raku++ itself, in about six minutes thanks to the startup time. The rule: no fully passing file may regress.
Gate 2 · t/run.raku
2,353 checks in about twenty minutes: regressions, --exe, --aot, JS, JIT, slim binaries, races, the sandbox, Arduino, memory leaks, Windows paths.
Gate 3 · perf-guard
A fixed set of kernels timed before and after. Getting slower counts as a regression too.
The interpreter is the oracle
The compiler isn't graded against Roast but against the interpreter: compile a program, run both, compare the output byte for byte. As of v5.8.0 --exe agrees on all 1,573 example and regression programs. --target=js --verify does the same per program and emits nothing unless stdout, stderr and exit status all match. People like this idea; pause on it.
It builds itself with Raku
tools/gen-unicode.raku reads the UCD and emits the C++ tables in src/. rakupp install and rakupp doc are Raku programs compiled into the binary, so the package manager can't work unless the interpreter is right about JSON, version ranges, run, paths and its own CompUnit API. The benchmark harness runs under Rakudo too, so the harness language can't bias the results.

Part 4 · 100.00% Roast

Every test Roast expects to pass

Roast · Meaning

Roast cf28a323c, with Unicode 18.0's test files, at v5.8.0. Let the number sit for a moment, then explain how it's counted.

The counts
219,395 of 219,395 tests that Roast expects to pass, with skip and todo left out; 221,034 of 221,034 counting every declared test. 1,425 of 1,425 files in spectest.data pass completely: all or nothing, file by file.
The climb
Fully passing files went from 656 at v4.0.0 to 1,425, with no regression allowed along the way. v4.0.0 was 91% of declared tests; the last 9% was the long tail, one file at a time.
Against Rakudo, carefully
On the older Roast 1f521d798, measured the same way on the same machine, Raku++ v5.1.0 passed 1,423 files and Rakudo 2026.08 passed 1,414. Say which commit it was, and that Rakudo isn't being judged here: Roast's todos are written for Rakudo.
What 100% doesn't say
Roast isolates features; real code combines a dozen modules at once. Numeric context on an array, nested hash access and pair keys all passed Roast and still printed wrong output in real programs. Roast is the floor, not the finish.

Part 6 · more than interpreting

One source, many targets

Run modes
Interpret
rakupp prog.raku: the default, and the mode that covers the whole language. A program can also run straight from a URL.
Bundle / AOT
--bundle embeds the source and re-parses at startup; --aot embeds the parsed AST. Both are standalone binaries that tree-walk, at interpreter speed.
Native
--exe -o prog transpiles to C++ and compiles it, with no interpreter inside. Anything it can't transpile yet falls back to --bundle automatically and says so, so --exe never refuses a program. Binaries are dead-stripped; bare --slim proves a feature unreachable before cutting it, and a wrong cut throws a catchable X::Feature::NotBuilt, never a wrong answer.
JavaScript
--target=js emits an ES module for Node, Bun, Deno or a page, with a source map back to the Raku lines; --standalone inlines the runtime; --verify checks it against the interpreter. Rats stay exact and .chars counts graphemes with the engine's own tables.
Arduino
--target=arduino: one sketch with no runtime, which the board's own compiler builds into firmware. See Arduino.
While running in progress
--jit and --cnp (copy-and-patch) compile hot loops while the program runs, with no C++ compiler needed. This is the v6 direction; don't promise numbers.

Speed: startup, then throughput

Speed

v5.5.0 against Rakudo 2026.09, 21 October, on an Apple M4 standing in for the usual M3, in one sitting with the engines interleaved. Compare with older sittings by ratio, not milliseconds.

Cold start
4.4 ms interpreting, 3.1 ms native, against Rakudo's 62.5 ms. That's what makes the CLI and one-liner story credible.
All eighteen kernels
--exe is ahead of Rakudo on all eighteen, from 1.08× to 135×; so is the interpreter, from 1.09× to 175×. The close ones are objects (1.18×) and multiwhere (1.08×), where MoarVM's spesh does its job, and multiwhere's binary bundles the interpreter. Say so before someone else does.
Don't over-claim
These are small kernels, startup included. v6 is the release about speed, with targets written down first: every perf-guard kernel at or below Rakudo at steady state.

Part 7 · in the browser, in your pocket, on a board

The playground: code, check and look it up, live

Playground

raku.online/play: the engine as WebAssembly, in the visitor's browser. Live demo, 60 to 90 seconds.

Coding: live re-run
With Live on, the program runs again a moment after you stop typing. Output streams as it comes, so ANSI animations like Game of Life play in the page.
Checking: an LSP in the page
The Raku++ language server runs in the browser: mistakes underlined as you type, help on hover, completions. It's the same lex→parse→lint pipeline that runs the code, so the squiggles can't disagree with the interpreter.
Documenting: doc links
Every construct in the program linked to its page on docs.raku.org, underlined in the editor and listed under the output. The same thing exists on the command line as --doc-links.
Input, sharing, privacy
A stdin strip for programs that read (get, lines, prompt, $*IN). A link that opens the playground with your code, or load a program from GitHub or another URL. Programs run in a Web Worker on the visitor's machine; the site is static files and no server runs your code.
Embedding it
A live editor on any static page is one script tag: 
<script src="https://raku.online/raku.js"></script>
<pre data-raku>say "Hello from an embedded editor!";</pre>

Three files copied into your own site make a complete install. The dropdown has the language showcases too: Python, interpreted by Raku, interpreted by C++ compiled to WebAssembly, in a fraction of a second. Keep a local copy in case the venue Wi-Fi is bad (rakujs/playground runs from any static server).

Learn Raku

What's in it
399 lessons of the Course of Raku in six parts, from variables to grammars, concurrency and the web; 1,000+ runnable examples with a Run button; 217 quizzes and 396 exercises, each solved in the built-in Playground and compared with the solution.

Raku as firmware

Arduino · Demo

The RISC-V board stays on the Build slide; this one fits in a pocket, so it's the one on the table.

What --target=arduino does
The program becomes one C++ sketch that names no runtime. The same file runs without a board too, on a simulated one, interpreted or compiled, and the gate checks both byte for byte. Tried on an Uno R4 WiFi (LED matrix and network included) and built for the Uno, Due and R4 cores.
Raku while building
Every constant is computed on your computer in full Raku (sin, .map, a file, use JSON::Native); the board gets only the result, stored in flash. An untyped variable is refused with a hint ("give it a native type, as in my int16 $x"): the board has 2 KB of RAM.
The demo

examples/arduino/raku-icon.raku draws the RAKU icon on the 12×8 matrix; frame runs while the program is built and packs the picture into the three 32-bit words the matrix library takes.

RAKUPP_ARDUINO_STOP=10 rakupp raku-icon.raku       # 1 · no board: drawn on stderr
rakupp --target=arduino raku-icon.raku -o raku-icon/raku-icon.ino
arduino-cli compile --fqbn arduino:renesas_uno:unor4wifi raku-icon
arduino-cli upload  --fqbn arduino:renesas_uno:unor4wifi -p <port> raku-icon
Before the talk
Plug the board in, run arduino-cli board list for the port, and compile once so the core is cached (the first compile is slow). If USB misbehaves, the board keeps its last firmware: flash it beforehand and just plug it into power. Bonus: wifi.raku puts the board on the network, but it needs WIFI_SSID/WIFI_PASS at build time, so don't show the password on screen.

Part 8 · the same binary, other hats

Tools that come built in

Toolbox

A fast slide. Pick one to talk about; the MCP server is the one that gets a reaction.

Checking before running
A variable nothing declares is refused before the program starts, and under -c, --bundle, --aot and --exe: a typo on line 90 doesn't show up after 89 lines of side effects. --lint has fourteen rules, several about silent bugs rather than style: new-arg-matches-no-attribute catches a typo'd named argument the default constructor would ignore, exact-power a Rat power that could take minutes. --json gives editors the findings as data.
Formatting, reading
--fmt has gofmt's promise: whitespace only, and three gates before a byte is written (the input parses, the result is the same program, formatting again changes nothing). --highlight is parse-aware, HTML and ANSI; --doc-links links every construct to its documentation; rakupp doc looks symbols up offline.
Running, watching
--detect-races reports data races between threads and where they happen; the tracer follows a run statement by statement; --profile prints a routine-level profile with the program's stdout untouched; the sandbox limits the file system and network; --watch, --repl-after, and perl's one-liner family (-n -p -a -F -i.bak, clustering the way perl's do).
Errors that say where
The call chain innermost-first with file, routine and line for every frame, and two-position errors: fail reports where the Failure was made and where it went off; await reports the worker's frames and the line that collected them.

Raku inside other things

Toolbox
AI agents: MCP
rakupp --mcp serves the interpreter over the Model Context Protocol, with two tools: raku, one persistent session per conversation with exact Rat and big-integer arithmetic, and raku-parse, grammars as deterministic text extraction with line/column/rule diagnosis when a parse fails. One line to register: claude mcp add raku -- /path/to/rakupp --mcp.
Jupyter, editors
rakupp --jupyter-install registers a kernel with no ZeroMQ, no Python module, no shared library: the binary speaks ZMTP and signs its own messages. rakupp --lsp speaks the Language Server Protocol, the same server the playground runs in the browser.
Six host languages not announced yet
librakupp is the interpreter behind a small C ABI, wrapped for Python, JavaScript (Bun), Go, Rust, C++ and the Wolfram Language: run Raku and get native values back, or parse with Raku grammars whose .made values come from Raku actions. Re-gated on every push; the README says it isn't announced yet, so mention it as work in progress.
Native extensions
The XS analogue: a distribution ships C beside its Raku, compiled against the ABI at install time, so the module versions independently of the compiler. An extension never sees Value; every Raku value crosses as an opaque handle.
Other people's software
Worth naming, because none of it is ours: RakuppLink in Wolfram's Paclet Repository (Anton Antonov); the Raku Playground with rakupp as one of four browser runtimes (Fernando Correa de Oliveira); Raku Koans, 105 lessons that Raku.js grades in the browser (Naoum Hankache); rakupp-dsci, the release matrix on another CI (Alexey Melezhik); and a Guix channel (4zv4l).

Part 9 · our own ecosystem

Modules, as installed

Modules · The sweep
The same store zef uses

rakupp install reads and writes ~/.raku, the CURI store zef fills, so a module installed by either tool works under either engine. It needs no Rakudo: the same index as zef, and it runs each distribution's own tests.

$ rakupp app.raku
app.raku uses 2 modules that are not installed:
  JSON::Fast, Terminal::ANSIColor
  to install them:         rakupp install app.raku
  to install them and run: rakupp --auto app.raku
Opt-in, always
It names every missing module at once, not just the first. Nothing is fetched unless you ask: --auto is opt-in, and so is module precompilation (--precomp-modules, which stores the parsed AST, not bytecode). A typo guard refuses use JSON::Mask meant as JSON::Fast instead of installing it.
A real package manager
Version pinning; install from a name, a path, a GitHub /tree/ subdirectory, a tarball or file://; uninstall, reinstall, --list, --check (a content-addressed audit that catches a truncated blob, not just a missing one), --gc, --to; rakupp test Foo runs a distribution's suite without installing it.
The sweep
Every distribution in the ecosystem, through its own test suite. On a fresh sweep at v5.0.0, 1,019 of 2,547 install and pass; Rakudo passes 1,791 through the same harness on the same machine, which is the ceiling to read the first number against; 738 can't pass there on any engine (libgsl, fontconfig, a network). v5.0.0 figure The sweep is the worklist, not a scoreboard: fixes land in the parser, the runtime and dispatch, never as a special case for a module. Every distribution is at raku.online/modules/ecosystem.

Part 10 · compatibility, and the fun problems

zef needs a JSON parser before modules exist

Chicken & egg

Tell it as a story: we ran zef, and it reached for a class that exists in no specification.

The problem

Every META6.json is JSON, so the installer has to parse JSON before it can install a JSON parser. On a bare Rakudo the only parser you can count on is the one the compiler carries for its own use, so zef uses that:

my \JSON = ::("Rakudo::Internals::JSON");
my %meta = JSON.from-json($file.slurp);
# reached dynamically: it compiles anywhere, and fails only at run time

An internal class became load-bearing public surface in all but name.

Not zef's fault
There's no dependency-free standard library for JSON, platform checks or directory walks. That gap is what Data::Native answers later.

Nine top distributions call another compiler's internals

Internals

A census of Rakudo::Internals across the top-200 battery.

What it means for us
Answering names that appear in no specification, cloned from observed behaviour and tested against the modules that call them. Answered today: JSON, IS-WIN, REGISTER-DYNAMIC. Still gaps: DIR-RECURSE (Pakku), NORMALIZE (SSL). LL-EXCEPTION is absent, but zef guards it with try … .?, so it quietly falls back to terse mode.

Two more places the implementation leaks through

nqp & VM
use nqp
JSON::Fast sits under about 170 distributions, and its hot paths reach for nqp::iseq_i, nqp::substr, nqp::push_s. NQP is Rakudo's bootstrap language, documented as internal and unspecified, so Raku++ implements the subset the ecosystem actually uses, with NQP's native-integer semantics. Optional demo: use nqp; say nqp::add_i(2, 3).
$*VM.name
On Raku++ it's cpp, and build scripts that only know moar or jvm stop with "Unknown VM; don't know how to build". RAKUPP_VM_NAME gets past them, and rakupp install retries LibraryMake's test as moar by itself, and says so.
The point
Neither is a bug in those modules. Both come from one implementation having been the only one for a long time.

Answer the alias, own the name

Two names
Rakupp::Internals::JSON
First-party: our own C++ codec under our own name, and what rakupp's own tools call. A typo'd Rakupp:: name is still an error; the namespace mustn't swallow mistakes.
Rakudo::Internals::JSON
Compatibility: the same codec under Rakudo's name, so zef, OpenSSL and Pakku run unchanged. On plain data the text is Rakudo's; on a Set or an object it's JSON::Fast's. Only the class name is Rakudo's; the code is original.
The plan of record
Removing the alias isn't realistic while zef calls it. Eventually the Rakudo spelling will say out loud that a program leans on another implementation's internals: a note, not a refusal. A bug this caught: JSON::Native's value-by-value suite showed the codec accepted trailing content (fixed in 9072beb).

Part 11 · our ::Native modules

JSON::Native, and Data::Native

::Native · Data::Native
One name, the engine's codec
use JSON::Native;
say to-json({ ok => True }, :!pretty);   # {"ok":true}
say json-backend();                      # engine

A normal distribution (META6, installed by zef) that the engine also answers itself: no file read, nothing installed. The contract is JSON::Fast's, down to the byte; what the C++ codec doesn't cover goes to a pure-Raku port of JSON::Fast built into the binary.

Stepping aside
The engine defers when an installed copy is newer, when -I or use lib points at one, or when you ask for a :ver, so the module's own suite always tests its own code. That list is what keeps the purpose of the older rule, "the compiler must not special-case a module name". The same idea covers CSV::Native, Digest::Native and Compress::Zlib::Native.
The name
It started as Rakupp::JSON and was renamed four days later: name a module for what it does, not for the engine it's fastest on.
use Data::Native
use Data::Native;
say to-json({ ok => True });            # json
say from-csv("a,b\n1,2\n", :headers);   # csv
say sha256-hex('abc');                  # digest, HMAC
say uncompress(compress('big'.encode)); # zlib, gzip, raw deflate
say crypt_random_buf(32);               # the OS CSPRNG

Five tags, thirty-two names; use Data::Native <json csv> takes just those. Every signature is copied character for character from the ecosystem module it stands in for. A program using it compiles to a standalone binary, with nothing left to find at run time. This is the dependency-free standard library whose absence made zef reach into Rakudo's internals: link back to the chicken-and-egg slide.

Honestly
The design is that on another engine the same line loads a distribution of the same name built from the usual ecosystem modules, so it's portable rather than Raku++-only. That companion distribution isn't published yet; say so.

The ecosystem: closing the gap between 1,019 and 1,791, one root distribution at a time. use in the browser: modules in the playground and under --target=js. Each target is a number written down before the code, so anyone can measure it again.
The ask, and the thanks
Try it on your code and report differences: every difference is either our bug or a spec question. Raku++ shares no code with Rakudo and wouldn't exist without it: without Roast, which says what Raku means; Rakudo, which answers when Roast is silent; and the authors of 2,547 distributions who wrote tests.

The project's documentation states its limits plainly. Saying them first is stronger than being asked.

  • No slangs, no macros. A deliberate limit, and the reason --exe exists. L10N::* works anyway, because a keyword table is not a grammar change.
  • 100% is per Roast's expectations. Skip and todo are left out of the 219,395; counting every declared test it's 221,034 of 221,034. The Rakudo comparison (1,423 vs 1,414 files) was on the older Roast 1f521d798.
  • The ecosystem is 1,019, not 1,791. Rakudo's number is the ceiling, and the figure is from the v5.0.0 sweep.
  • objects and multiwhere are close. 1.18× and 1.08× compiled: method dispatch is where spesh still nearly keeps up, and those are small kernels with startup included.
  • NativeCall gaps. C structs passed or returned by value are unsupported, and callbacks a C library fires later from its own thread are detected and ignored rather than run.
  • Native recursion overflow is fatal. Direct native calls under --exe reach about 1.27 million levels, but overflow there is a SIGBUS, not a catchable X::Recursion.
  • Not announced yet: the host-language bindings. In progress: --jit / --cnp. Not published: the Data::Native companion distribution.
  • Rakudo is the complete one. Raku++ is a young implementation growing toward the same language, and the two share a north star in Roast.

Closures, WhateverCode, junctions, lazy sequences (1, 2, * + * ... Inf), gather/take and take-rw, feeds ==>, ∘, and the S07 iterator protocol. A Seq drained by its one holder drops what it handed out, so a lazy read keeps only what will be read again.

Concurrency & real parallelism

ASYNC.md · PARALLEL-SPEEDUP.md
Parallel by default
Worker threads run interpreter code concurrently; RAKUPP_GIL=1 is the escape hatch to the cooperative mode. Lock and Semaphore are real, and --detect-races finds the places threads collide.
The measured number
3.25× for four start blocks against a plain loop doing the same work, against 0.98–1.00× under the GIL. The honest control: N=1 measures 0.85×, the thread setup you paid for and didn't get back.
The async surface
Promise/start/await, Supply/react/whenever, Channel, Proc::Async, atomicint with ⚛, IO::Socket::Async, and IO::Socket::Async::SSL over the system OpenSSL through Raku++'s own NativeCall.

Talking to C: NativeCall

FFI.md · HTTPS.md
libffi, but no dependency
is native calls through libffi that is dlopened at run time and never linked. Where no libffi can be loaded, anything a fixed prototype can't express throws rather than computing garbage.
What it covers
Declared widths, any number of arguments, CArray, CStruct, CUnion, Bufs filled in place, is rw out-params, nativecast, cglobal, variadics, and synchronous callbacks as real ffi_closures, so qsort works.
The HTTPS story
One real HTTP/1.1 200 OK over TLS was a chain of independent bugs, each hidden behind the last, and nearly every one turned out to be a general correctness bug.

Footprint: memory and stack

MEMORY.md
Resident memory
A hello-world costs 2.7 MB resident interpreted and 5 MB native. The gigabyte of main stack is address space, not RAM, committed page by page as recursion deepens.
Recursion depth
~50,500 levels interpreted, with a guard that leaves you a catchable X::Recursion; ~1,270,000 for direct native calls under --exe, where overflow is fatal.
Reading big things
Text readers (.lines, .words, $*IN.lines, a child's .out.lines) read a 256 KiB window at a time: 100 MB through .get peaks at 14 MB, and four million mapped Hashes in a for at 13 MB.
