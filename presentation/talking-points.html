What it is — the opening claim

README.md · OVERVIEW.md
From scratch, not a fork
A complete implementation of the Raku language in C++17 with no third-party dependencies: hand-written lexer, Pratt parser, tree-walking evaluator, bignum, Unicode tables and regex engine. It shares no code with Rakudo and was built without reading Rakudo's source. Since 2026-08 it studies Rakudo and MoarVM at the design level and ports nothing.
Interpreter and compiler, one binary
The same executable tree-walks a script or compiles it to a standalone native binary — and, transpiled a second way, to JavaScript, or compiled to WebAssembly to run in a browser.
Measured against Roast
The official Raku specification suite is the target and the scoreboard. The motto: any compiler that can run Roast can be officially called a Raku compiler. The harness is itself written in Raku and run by Raku++.
Two revisions, gated
6.d by default, 6.e under use v6.e.PREVIEW — 50 of 51 tracked 6.e changes match Rakudo, 46 of them properly gated on the pragma. The revision belongs to the code: a 6.e module keeps its semantics inside a 6.d program without changing that program's own. Rakudo differs here — use-ing a 6.e module loads CORE.e process-wide.

Exact numbers

FEATURES.md · BENCHMARKS.md

The demo that lands in every room, and the one that is genuinely fast here.

The whole tower, exact

Arbitrary-precision Int (a hand-rolled bignum, base 1e9), exact Rat on BigInt numerator and denominator, Num, Complex, and allomorphs. / yields a Rat; **, %, div, mod, %% and every comparison are exact.

say 0.1 + 0.2 - 0.3;      # 0     — exactly
say 2 ** 1000;            # all 302 digits
say (1/3 + 1/6).nude;     # (1 2)
And it is quick
The bigint kernel runs at 4.6 ms compiled against Rakudo's 160.9 ms — a 35× lead — and beats mutsu's num-bigint by 2.0× despite being hand-rolled to keep the zero-dependency rule. (It was a 3.5× loss until an eight-carry-chain multiply landed in v3.24.0. Good story for a talk.)
Literal surface
Radix 0x 0o 0b 0d and :16<ff> / :36<aZ>, _ separators, exponents, leading-dot fractions, imaginary 4i, ∞/Inf/NaN, superscripts ², and string→number coercion that parses all of it including Complex and the Unicode minus −.

Batteries in the compiler — JSON, CSV, digests, zlib, CSPRNG

DATA-NATIVE.md

The strongest "you can't do this elsewhere" slide: use Data::Native is answered by the compiler itself. No file is read, no module is loaded, no dependency is resolved.

Five tags, thirty-two names
use Data::Native;

say to-json({ ok => True });            # JSON
say from-csv("a,b\n1,2\n", :headers);   # CSV
say sha256-hex('abc');                  # digests and HMAC
say uncompress(compress('big'.encode)); # zlib / gzip / raw deflate
say crypt_random_buf(32);               # the OS CSPRNG

json · csv · digest (MD5, SHA-1, SHA-224/256/384/512, their -hex twins, HMAC) · zlib (compress, uncompress, gzslurp, gzspurt, crc32, adler32) · random.

Portable, not proprietary
Every signature is copied character for character from the ecosystem module it stands in for — JSON::Fast, CSV::Native, Digest::*, Compress::Zlib, Crypt::Random. The same line loads a real distribution of that name on Rakudo, so the program runs unchanged there. *-backend() says which answered.
The consequence worth stating
A program using Data::Native compiles to a standalone binary, because there is nothing left to find at run time. A program that reaches for the installed distribution directly does not.

Speed — startup, then throughput

BENCHMARKS.md

Fifteen kernels, one machine (Apple M3, Darwin 24.6), three engines interleaved in the same sitting so a load spike lands on every lane instead of one column.

Cold start
3.0 ms interpreting, 2.5 ms native — a small binary with no VM to spin up. mutsu starts in 4.4 ms; Rakudo in 75.6 ms. Fast enough to shell out to in a loop, which is what makes the CLI and one-liner story credible.
Against Rakudo
--exe wins fourteen of fifteen kernels; the tree-walking interpreter wins eleven and is level on three. Against mutsu the interpreter wins 14/15 and --exe sweeps all 15.
The one that goes the other way
objects — class/has/method dispatch, the shape most real Raku is written in. Rakudo leads it by 1.6× compiled and 2.3× interpreted. Neither from-scratch engine is close to spesh there. Say it before someone else does; it also leads mutsu on that kernel by 7.7×.
Why strcat is so lopsided
String building with ~= appends in place in every mode, so it is O(n) rather than O(n²) — 10.8× ahead of Rakudo even interpreted, 29.1× compiled.

Footprint — disk, memory, stack

MEMORY.md · CLI.md
On disk
The rakupp binary — interpreter and compiler — is 14.4 MB. A typical --exe output is ~10 MB, or 6.8 MB under bare --slim. Size is almost entirely the linked runtime, so it stays flat as the program grows.
--slim, and what it proves
Compiled binaries are dead-stripped by default. Bare --slim runs a scan that proves a feature unreachable before cutting it; anything it cannot decide is kept, and a force-full trigger (EVAL, symbolic reference, indirect method call, interpolated subregex) keeps everything and says so. A wrong cut throws a typed, catchable X::Feature::NotBuilt — never a crash, never a wrong answer.
Resident memory
A hello-world costs 2.7 MB resident interpreted, 5 MB native. The gigabyte of main stack is address space, not RAM — committed page by page as recursion deepens.
Recursion depth
~50,500 levels interpreted, with a guard that fires while 2 MiB of headroom remains so you get a catchable X::Recursion rather than a signal. Direct native calls under --exe reach ~1,270,000 — but overflow there is fatal, not catchable, and that limitation is documented rather than hidden.
Guardrails, stated
An 8-million-step regex budget so a pathological pattern degrades to a fast failure; sprintf width and precision capped at 10,000,000; infinite ranges never materialize; env→closure cycles collected at frame teardown (a 300k-call loop went from retaining ~425 MB of dead frames to ~3 MB).

Six ways to run the same program

ARCHITECTURE.md · NATIVE.md · JS.md · rakujs/

One front end, several back ends — and the tagline that goes on the slide: write it, run it, compile it.

Interpret
rakupp prog.raku — the default, and the only mode that covers the whole language.
Bundle / AOT
--bundle embeds the source and re-parses at startup; --aot embeds the parsed AST. Both are standalone binaries that tree-walk, so they run at interpreter speed.
Native
--exe transpiles the AST to C++ and compiles it — no interpreter inside. Anything it cannot yet transpile (mainly grammars) falls back to bundling automatically and says so, so --exe never refuses a program. -O turns on the code generator's optimizer.
JavaScript
--target=js emits an ES module that runs under Node, Bun, Deno or a browser, with prog.js.map mapping every generated line back to its Raku line. --standalone inlines the runtime into one file; --verify runs the program under both the interpreter and the JS host and emits nothing unless stdout, stderr and the exit status match byte for byte. Rats stay exact, .chars counts graphemes with the engine's own UAX #29 tables.
The browser — Raku.js
The same interpreter compiled to WebAssembly, running client-side with no server. A live editor on any static page is one script tag: 
<script src="https://raku.online/raku.js"></script>
<pre data-raku>say "Hello from an embedded editor!";</pre>

Three files copied into your own site is a complete install — nothing has to be loaded from raku.online. It also powers raku.online/play and an 18-lesson interactive tour.

The language it actually runs

FEATURES.md · REFERENCE.md
Objects & the metamodel
class / role / grammar, multi-method dispatch, BUILD/TWEAK, enums, does/but runtime mixins, .^name/.^methods/.^mro/.^add_method/.^parameterize, routine .wrap, and augment that reopens built-in types (augment class Int reaches 3.method).
Signatures & dispatch
multi/proto, type / literal / where constraints, :D/:U smileys, named and slurpy parameters, sub-signature destructuring (with multi dispatch on the destructured arity), coercion types Str(Cool), callsame/nextsame/samewith.
Metaprogramming
User-defined operators in all six categories — infix, prefix, postfix, term, circumfix, postcircumfix — with working precedence traits (is tighter, is looser, is equiv, is assoc), and meta-operators that compose over user ops: [myop], >>myop<<, Z§, $x myop= y. The operator table changes mid-parse, in one pass.
Functional & lazy
Closures, *-currying (WhateverCode), junctions (any/all/one), lazy sequences (1, 2, * + * ... Inf), gather/take (and take-rw, which writes back), feeds ==>, composition ∘, and the full S07 iterator protocol with the IterationEnd sentinel.
Phasers & control
BEGIN CHECK INIT END ENTER LEAVE FIRST NEXT LAST CATCH CONTROL, labeled loops, temp/let, given/when, with/without, statement modifiers including chained ones.
Also in the box
Shaped arrays (my @a[2;2]) with structural validation, Set/Bag/Mix, Proxy, a POD DOM as real Pod::Block objects, resumable exceptions, Failure, and the full Test API — which is why the Roast harness can be self-hosted at all.

Unicode — the part that is genuinely complete

UNICODE.md

Tables generated from UCD/UCA 17.0 by a Raku program that Raku++ runs — the engine generates part of its own C++ source.

Graphemes
Full UAX #29 including GB9c Indic conjuncts, emoji ZWJ sequences, skin tones and flags. GraphemeBreakTest-* and emoji-test.t (3,825 tests) fully pass. .chars, .comb and .flip all count clusters.
Collation
unicmp/coll from DUCET 17.0, with contractions including discontiguous matching and implicit weights: all 8,271 conformance tests pass.
Normalization & names
NFC / NFD / NFKC / NFKD including Hangul; every nf*-*.t and mass-equality.t passes. Character names in both directions, including algorithmic CJK / Tangut / Nushu / Hangul-syllable names. Numeric values as exact Rats, Unihan included — unival('千') is 1000.
In regexes
General category short and long, real Scripts.txt scripts, blocks (<:InArabic>), bidi classes (<:bc<L>>), and binary properties from DerivedCoreProperties + PropList — negated and inverted forms too.

Regexes & grammars

FEATURES.md · book/ch/23-ltm.md
True LTM
Longest-Token Matching by a real NFA ranker — the default since v3.0.0, replacing a probe-based approximation. | ranks by longest declarative prefix as the spec says; || is sequential.
The grammar surface
token/rule/regex, .parse/.subparse/.parsefile, action classes with make/.made, subrules and subrule aliases, and capture aliases in all four flavours — numbered $7=(…), named, list-valued @<x>=, hash-valued %<x>=.
Beyond the common set
Conjunction A & B, composed character classes that add and subtract members (<+alpha-[b]>), the full adverb set (:g :ex :x :nth :i :ignoremark :samecase :sigspace), non-mutating S///, callable .subst.
The demo that sells it
Five language interpreters in showcase/ — Scheme, Forth, JavaScript/TypeScript, Perl 5 and Python 3 — each built on a Raku grammar. Plus a grammar of Raku that parse-checks Raku source with rakupp itself, restating the fifteen precedence levels of src/Parser.cpp as grammar rules.

Concurrency & real parallelism

ASYNC.md · PARALLEL-SPEEDUP.md
Real OS threads, parallel by default
True CPU parallelism has been the default since v3 — RAKUPP_GIL=1 is the escape hatch back to the cooperative mode. Worker threads run interpreter compute concurrently; registers and stacks are thread-local, symbol tables freeze once concurrency engages, and Lock/Semaphore become real. ThreadSanitizer-clean, zero Roast regressions.
The measured number
2.93× on four performance cores (N=4), against 0.98–0.99× for the same program under the GIL at every thread count. The honest control is there too: N=1 measures 0.85× — the thread setup you paid for and did not get back.
The full async surface
Promise/start/await, Supply/react/whenever/supply with a long combinator list, live Supplier, Channel, Thread, Proc::Async with bind-stdin pipelines and a real .kill, and atomicint with the ⚛ operators.
Networking
IO::Socket::Async for clients and servers, signal() for graceful shutdown, and IO::Socket::Async::SSL over the system OpenSSL through Raku++'s own NativeCall. Four servers on raw sockets ship as showcases: a pastebin, a concurrent chat server, a key-value store with its own protocol, and rakus, a static-file HTTP server.

Talking to C — NativeCall

FFI.md · HTTPS.md
libffi, but no dependency
is native calls a C function via dlsym, marshalled by libffi that is dlopened at run time and never linked — so the binary keeps the zero-dependency promise. --ffi-info reports what it found. Where no libffi can be loaded, calls fall back to a fixed prototype and anything it cannot express throws rather than computing garbage.
What it covers
Arguments and returns at their declared width (num32 is a real C float), no cap on argument count, mixed int+float lists, CArray, CStruct, CUnion, Buf/Blob filled in place, is rw out-params with copy-back, nativecast, cglobal, variadics (a slurpy marks where ... begins — same spelling as Rakudo), and typed synchronous callbacks as real ffi_closures, so qsort works.
The HTTPS story
A ready-made narrative: getting one real HTTP/1.1 200 OK over TLS was never one feature — it was a chain of independent bugs, each hidden behind the last, and nearly every one turned out to be a general correctness bug. Roast numbers went up the whole way.

Modules & the ecosystem

MODULES.md · CLI.md · ECOSYSTEM.md
Its own installer, sharing zef's store

rakupp install writes the same CURI store zef and Rakudo share, so a module installed by either tool is picked up by use under either engine. It is a ~1,840-line Raku program compiled into the binary — as is rakupp doc.

rakupp install JSON::Fast
rakupp install ./my-dist
rakupp install https://github.com/ash/raku-modules/tree/main/Prompt-Hidden
rakupp test Foo          # build + run Foo's own suite, never install Foo
A real package manager
Version pinning, additive installs, install from a name, a path, a GitHub /tree/ subdirectory (monorepos), a tarball or file://; uninstall, reinstall, --list, --check (a content-addressed integrity audit that catches a truncated blob, not just a missing one), --gc, --refresh, --to.
The sweep
All 2,530 distributions of the Raku ecosystem are run against rakupp and the engine is fixed until they install and pass their own suites. 824 pass today; another 274 never reached their own tests because a dependency failed first — that cohort is the current lever. Every distribution, with how it ran, is browsable at raku.online/modules/ecosystem.
Real applications, unmodified
The raku-course static-site generator regenerates the entire ~1,500-page Raku course byte-for-byte identically to Rakudo, including the real zef-installed YAMLish. The covid.observer site builder runs end to end. modinfo does its work through 17 zef distributions and produces identical output under both engines.

Integrations — Raku inside other things

bindings/ · EMBEDDING.md · EXTENSIONS.md · MCP.md · JUPYTER.md
Six host languages not announced yet
librakupp is the interpreter behind a small C ABI, wrapped for Python, JavaScript (Bun), Go, Rust, C++ and the Wolfram Language. Each gives the same two things in its own idiom: run Raku — evaluate source, call Raku routines with host values, read results back as native types — and parse with Raku grammars, where the grammar stays a .raku file and .made values are computed by Raku actions during the parse. Two smoke gates re-run everything the guides claim, on every push.
Embedding, in C
rk_new / rk_eval / rk_eval_file / rk_call / rk_run. An interpreter is a session: define a sub in one rk_eval, call it in the next. A Raku exception never unwinds through your frames. Raku.js and rakupp --mcp are both written against this same API.
Native extensions — the XS analogue
A distribution ships C alongside its Raku, the build step compiles it against the ABI at install time, and the routines become ordinary Raku subs. The point: the module versions independently of the compiler. An extension never sees Value — every Raku value crosses as an opaque handle, because sizeof(Value) went 392 → 376 → 344 → 208 → 128 bytes and will move again.
AI agents — MCP not announced yet
rakupp --mcp serves the interpreter over the Model Context Protocol on stdio, giving clients two tools: raku, one persistent session per conversation with exact Rat and big-integer arithmetic, and raku-parse, grammars as deterministic text extraction with line/column/rule diagnosis when a parse fails. One line to register: claude mcp add raku -- /path/to/rakupp --mcp.
Jupyter
rakupp --jupyter-install registers the binary as a kernel. One interpreter serves the whole notebook, output streams as it is produced, a dying cell leaves the session intact, and jupyter-display hands the frontend HTML or SVG. No ZeroMQ, no Python module, no shared library — the binary speaks ZMTP and signs its own messages, because this project links no third-party libraries. The gate is a Jupyter client written in Raku with its own HMAC-SHA256 pinned to the RFC 4231 vectors.
Editors
rakupp --lsp speaks the Language Server Protocol — diagnostics only, from the same lex→parse→lint pipeline that runs your code, so the squiggles can never disagree with the interpreter. needs review For an editor that does not speak LSP, -c --json and --lint --json emit findings as a JSON array.
Other people's software
Worth naming on a slide, because none of it is ours: RakuppLink in Wolfram's official Paclet Repository (Anton Antonov); the Raku Playground offering rakupp as one of four browser runtimes (Fernando Correa de Oliveira); rakupp-dsci, the release matrix ported to another CI (Alexey Melezhik); and a personal Guix channel (4zv4l).

A desktop GUI, with react as the event loop

showcase/gui
Real windows, no glue code
The same NativeCall machinery that talks to libsqlite3 is pointed at the Objective-C runtime and gets a real desktop app: NSWindow, NSTextField, NSButton, reached through objc_msgSend. The framework on top is the GUI::Wings module; the backends are Cocoa and GTK.
The idea worth showing
The event loop is not a callback registry — it is react, with a button's clicks, a one-second clock and SIGINT as three whenever streams. A click crosses from AppKit into a Raku closure through a runtime-minted Objective-C class.
And it runs on Rakudo too
No NSRect ever crosses the FFI — only NSPoint/NSSize, two doubles, which both macOS ABIs pass like two num64s — so the identical module serves arm64 Raku++ and an x86-64 Rosetta Rakudo, unchanged.

RakuAST, a formatter, and Raku in your own language

CHANGELOG.md (v3.28.0) · FEATURES.md · faq/l10n.md
RakuAST is in, end to end
The 489-class hierarchy plus every operation over it: .AST builds the tree, .DEPARSE renders it back to Raku, .EVAL runs it, visit-children walks it, .rakudoc answers a unit's documentation blocks, and rakupp --rakuast prints the whole thing with each node's Raku beside it.
It is a view, not a second front end
Nothing is built until .AST is called, so the ordinary path pays nothing for it — worst +2.7%, mean −1.3% over sixteen kernels against v3.27.0 built from source and interleaved A/B/A/B. The measurement is why: as the internal tree, RakuAST is ~2.3× the nodes and ~2.1× the visits in the fib inner loop, and this engine walks its tree forever.
How complete is the view
Over the raku-corpus programs both engines can tree, it carries 72.9% of the nodes Rakudo's own trees carry. rakupp --rakuast prints ours, tools/rakuast-oracle-dump.raku prints Rakudo's, and the comparison is a diff. The largest gap left is the Regex::* subtree.
use L10N::DE; — and the rest of the file is German
Eleven installed languages run: German, Japanese, Afrikaans, Welsh, Esperanto, French, Hungarian, Italian, Dutch, Portuguese, Chinese. Upstream this is a slang mixed into $*LANG during the parse; this engine has no grammar object to mix into — but an L10N slang is a table of keyword spellings, and our lexer hands every keyword to the parser as a plain identifier, so it is a rewrite of the token stream off the same table .AST($lang) reads. Rakudo 2026.08 needs RAKUDO_RAKUAST=1 for these modules; this engine needs no flag. Two differences are documented rather than hidden: the rewrite is whole-unit where upstream is lexical, and a declarator that changes how the lexer scans what follows it (token, rule) cannot be reached by a token rewrite.
rakupp --fmt
A source formatter with gofmt's promise: zero configuration, run it on every save without reading its output. Whitespace only — Raku's whitespace is semantically significant, so it rewrites the space between classified spans and never the bytes inside one — and three gates run before a byte is written: the input must parse, the result must be the same program, and formatting it again must change nothing. -i / -i.bak rewrite in place, --check names files that would change, --diff shows what.

The command line and the developer loop

CLI.md · LINT.md · TRACER.md · CACHING.md
Undeclared variables are refused
Before a program starts — and under -c, --cpp, --bundle, --aot and --exe — rakupp walks the whole unit and refuses it if a variable is used that nothing declares. A typo on line 90 no longer shows up after 89 lines of side effects.
Errors that tell you where you are
The call chain innermost-first with file, routine and line for every frame; the source line of the one it came from; folded recursion; and two-position errors — fail reports where the Failure was made and where it went off, await reports the worker's frames and the line that collected them.
Analysis without running
--lint carries eleven rules over the AST, several of which are about silent bugs rather than style — new-arg-matches-no-attribute catches a typo'd named argument that the default constructor would silently ignore. --json emits findings as data.
Profiling
--profile prints a routine-level wall-time profile after the run, exact call counts included, with recursion counted once. The program's own stdout is byte-identical to an unprofiled run, and the disabled hooks cost nothing — there is no separate profiling build.
The perl one-liner family
-n, -p, -a, -F, in-place -i.bak, and they cluster the way perl's do: rakupp -pi.bak -e '$_ = $_.subst("a","b")' *.txt. Flags are position-independent.
Everything else on the CLI
--watch (rerun on change, including modules under lib/), --highlight (parse-aware, HTML and ANSI), rakupp doc (offline symbol lookup with the guides compiled into the binary), --completions for bash/zsh/fish, --repl-after (a session on the program's live state, like python -i), --trace, --stagestats, --seed, --stack-size, --env-file, RAKUPP_OPT, NO_COLOR.
Opt-in parse cache
Off by default — nothing is written to your disk until you ask. --precomp-modules caches the parse of everything a program uses (use XML: 6.0 → 4.8 ms); --precomp-files pays from about a thousand lines up. What is stored is the AST, not bytecode, because the tree already is the compiled form.

The engine builds itself with Raku

DOGFOODING.md

A theme rather than a feature, and a good closing one: every run of the toolchain is a real workout for the interpreter.

The Roast harness is Raku
The entire coverage figure is measured by Raku++ — and thanks to the ~2 ms startup, all 1,464 spec-test files run in about 3½ minutes. Refreshing the numbers is a coffee break, not an overnight job.
It generates its own source
tools/gen-unicode.raku reads 40k+ lines of UCD data and emits the C++ character-name, category and numeric-value tables in src/.
Two Raku programs live inside the binary
rakupp install and rakupp doc are not C++ subcommands — they are Raku programs compiled in as byte arrays, which the binary loads out of itself and interprets. The package manager is written in the language the engine implements, so it cannot work unless the interpreter is right about JSON, version ranges, run with captured output, path handling and its own CompUnit API.
Even the benchmark harness
It also runs under Rakudo, so the harness language cannot bias the results.

Have these ready

ROADMAP.md · HIGHLIGHTS.md

The project's own documentation states its limits plainly. Saying them first is stronger than being asked.

  • No slangs. Pluggable syntax needs a grammar object to mix a role into, and nine seams would have to grow one; the plan is written and the emulation route was rejected. RakuAST landed in v3.28.0 and was not the blocker — and the L10N::* family works here anyway, because a keyword table is not a grammar change.
  • 46% of Roast files, not 91% of them. The 91% figure is per individual test. Both are quoted because the file bar is the stricter, more honest one, and the methodology is written down.
  • objects is Rakudo's kernel. Method dispatch and attribute access — the shape most real Raku is written in — is where spesh still wins, by 1.6× compiled.
  • C structs by value are unsupported in NativeCall, and callbacks a C library stores and fires later from its own thread are detected and ignored rather than run.
  • The bindings and the MCP server are committed but not announced. They are gated on every push; the surface may still move.
  • The LSP server is diagnostics only and flagged as needing review; the VS Code extension has never been published.
  • Rakudo is the complete one. The documentation says so on every comparison page — Raku++ is a young implementation growing toward the same language, and the two share a north star in Roast.
